# RepoPilot 3 分钟演示脚本

## 演示前准备

在仓库根目录执行：

```powershell
python -m pip install -e '.[api,mcp,dev]'
$env:REPOPILOT_REPO_PATH = "$PWD/demo/cases/pagination_off_by_one"
python -m uvicorn repopilot.app:app --app-dir src --host 127.0.0.1 --port 8000
```

打开 `http://127.0.0.1:8000`。输入 Issue：`第一页漏掉第一条订单，list_orders 的 offset 错误`；测试目标保持 `tests`。

## 0:00–0:35｜Code RAG 与 Agent 展示

先在 Code RAG Copilot 提问：`list_orders 的分页逻辑在哪里？`。

“RepoPilot 会先识别意图，再从 6 个只读工具中选择代码搜索，运行混合检索并流式回答。右侧 Agent Execution 展示查询改写、工具、引用数和耗时；回答引用可以直接打开对应代码。会话会按仓库持久化。”

## 0:35–1:00｜从问答进入可执行任务

输入准备好的 Issue，点击“开始分析”，展示计划和 `orders.py`、`test_orders.py` 证据。

“对话层始终只读；真正的代码修改必须进入另一条受控状态机，不能因为模型回答了就绕过审批。”

## 1:00–1:25｜先证明问题存在

点击“运行基线复现”。展示原仓库 pytest 失败输出。

“补丁建议不会在一开始出现。只有指定的测试在原仓库真实失败，Agent 才能继续；如果测试原本是通过的，或者测试路径不合法，流程会被安全阻断。”

## 1:25–1:55｜人工审批与最小 Diff

展示待审批建议和原因：页码是从 1 开始，因此第一页的 offset 应为 0。点击“批准并生成隔离 Diff”。

“批准后它不会修改这个演示仓库。RepoPilot 会创建隔离工作区，只应用一个最小的文本替换，并把 Diff 留给人工检查。”

## 1:55–2:25｜同一目标的回归验证

点击“运行验证与审查”。展示 pytest 通过和 Reviewer 结论。

“它使用的是刚才相同的测试目标。Reviewer 会同时检查：修复前是否失败、修复后是否通过，以及补丁路径是否安全，所以不是只看一次绿灯。”

## 2:25–2:45｜可追溯性和边界

展示事件轨迹、测试输出、Diff 或 Markdown 报告。

“任务、代码证据、补丁建议、测试输出和审查结论都保存在 SQLite。MCP 接口只读代码和运行受限测试，不允许外部 Agent 绕过审批直接写补丁。”

## 2:45–3:00｜工程质量与收尾

打开仓库 README 顶部的 CI 徽章，或 GitHub Actions 页面。

“项目现有 30 个测试、3 个可复现修复案例和 4 个 RAG Eval 案例；RAG 同时检查来源、符号、Top‑1、意图与工具。当前版本故意只自动修复受控场景；未知问题会停在证据阶段。”

## 常见追问的短答

| 追问 | 回答 |
| --- | --- |
| 为什么不直接让模型改？ | 模型只能协助计划或候选建议；审批、路径校验、隔离环境和回归验证是确定性安全边界。 |
| 为什么要基线失败？ | 没有失败基线就无法证明补丁解决了目标问题，可能只是碰巧测试通过。 |
| 为什么需要隔离工作区？ | 防止实验性修改污染开发者当前分支，也让 Diff 和验证结果可单独审查。 |
| 下一步怎么扩展？ | 增加更多受控评估、引入候选补丁排序，再逐步支持更多语言和安全沙箱。 |
